## ⚠️ Important Scoping Note (Read First)

Three source artifacts have now been analyzed: `raden-motion.zip`, `betawi-motion.zip`, and `arjuna-tema-foto.zip`. **None of these are template source code.** Each is a single rendered HTML snapshot of a different live page under the same WordPress installation (`webinvite.id/raden-motion/`, `webinvite.id/betawi-motion/`, `webinvite.id/arjuna-tema-foto/`), generated by the same stack (Elementor + a commercial premium plugin called `weddingpress`, part of a product called "Web Invite" / WeddingPress.net, cached via LiteSpeed).

Consequences for this PRD:

- There is no original React/Vue/PHP source to "migrate" line-by-line for any of the three. This is a **behavioral rebuild**: we reverse-engineered the feature set, data shape, and UX from the rendered markup and inline scripts of all three samples, then designed one system capable of reproducing and extending all of them — plus future templates — on your target stack.
- No component in any of the three artifacts is reusable as code. Reuse is limited to: visual/UX reference, copy structure, and the font/asset list (which must be re-licensed or replaced — see Risk Assessment).
- Everything under "Current Architecture Analysis" and "WordPress Dependency Mapping" below reflects what is **observable from the static exports**, not confirmed internal WordPress schema (custom post types, ACF field keys, DB tables). Where the internal shape is inferred rather than confirmed, it is marked **(inferred)**.
- **Critically, the three templates are not identical in feature set** — see "Template Catalog & Variability" below. This directly shapes the folder structure and data model: the platform must treat "which sections/fields exist" as a per-template, data-driven property, not a fixed set hardcoded once.

## Executive Summary

You Are Invited is currently a wedding-invitation landing page served from a WordPress installation (`webinvite.id`) using Elementor Pro as a page builder and a premium plugin (`weddingpress`) for domain-specific widgets (audio player, guest-name personalization, RSVP/Ucapan, gift/bank-transfer block). All content — couple names, event schedule, gallery, love-story timeline, gift accounts — is either hardcoded into Elementor-rendered markup or pulled from WordPress's native comment system (for guest wishes).

This project replaces that entire stack with a standalone, self-hosted application:

- **Frontend:** React + TypeScript + Vite + TailwindCSS + shadcn/ui, reproducing all observed sections (cover screen, hero/countdown, couple profiles, event details with maps, gallery, love story timeline, RSVP + guest wishes, hashtag, livestream, wedding gift, background music, guest-name personalization via URL parameter).
- **Backend:** Hono (TypeScript), exposing a REST API for invitation content, RSVP submissions, and guest wishes.
- **Database:** SQLite, accessed via Drizzle ORM, with a schema designed fresh (not migrated) to support multi-tenant invitations (since this appears to be a template product serving many couples, not a single wedding site).
- **Admin panel:** A new authenticated dashboard for CRUD over all invitation content, replacing the WordPress `wp-admin` + Elementor editing workflow entirely.
- **Deployment:** Dockerized, no WordPress, no PHP, no MySQL/MariaDB, no wp-json, no Elementor.

The result is a lighter, fully self-owned stack matching your existing self-hosting practice (Docker Compose, Proxmox, Cloudflare Tunnel), with no recurring dependency on a third-party WordPress plugin license (`akses.weddingpress.net` member area).

## Problem Statement

The current implementation has these concrete problems, observed directly in the exported markup:

1. **Third-party plugin lock-in.** The RSVP/Ucapan widget, audio player, and guest-name personalization are all implemented by a closed-source commercial plugin (`weddingpress`) gated behind a member portal (`akses.weddingpress.net`). You do not control this code and cannot extend it.
2. **Guest wishes stored as WordPress comments.** "Ucapan" (guest greetings) use `wp-comments-post.php` plus a comments-UX plugin (`CUI_WP`). This means guest-wish data lives inside WordPress's `wp_comments` table, tied to a WordPress post ID, with no clean API contract.
3. **All assets are hot-linked to the WordPress media library.** Every font (30+ custom `@font-face` declarations) and every image is served from `webinvite.id/wp-content/uploads/...`. A standalone app cannot depend on another site's uploads folder.
4. **No dynamic data layer for invitation content.** Couple names, dates, venues, gallery images, and story entries are baked directly into server-rendered Elementor HTML — there is no per-invitation JSON/API contract today, which means every new couple's invitation is presumably a duplicated Elementor page (WordPress post) rather than templated data. This does not scale and makes bulk operations (analytics, exports, theming) impractical.
5. **Heavy, slow stack.** Elementor + Elementor Pro + 5 additional plugins + LiteSpeed cache is a lot of runtime weight for what is fundamentally a static content page with three write operations (RSVP, wish, gift-copy interaction).
6. **No first-class admin experience for the actual users of this product** (engaged couples). WordPress's `wp-admin`/Elementor editor is not designed for a non-technical bride/groom to fill in their own event details, upload photos, or moderate guest wishes.

### Observed page sections (in DOM order)

1. **Cover/gate screen** — "The Wedding Of [Names]", "Kepada Yth: [Guest Name]", a "Buka Undangan" (Open Invitation) button that gates the rest of the content and is the user-gesture trigger required to autoplay background audio.
2. **Hero** — couple names, wedding date, countdown timer (days/hours/minutes/seconds), a Quranic verse (Islamic wedding — content is culturally/religiously templated, must remain configurable per invitation).
3. **Greeting/opening text** — Arabic-Islamic greeting formula ("Assalamu'alaikum Wr. Wb...") — static per-invitation text field.
4. **Couple profiles** — two blocks (bride/groom), each with: full name, "child of [Father] and [Mother]" lineage line, Instagram handle/link, and (implied) a photo.
5. **Event details** — two repeated blocks (Akad Nikah / Resepsi Nikah), each with: day name, date, time range, venue name, venue address, and a "Lihat Lokasi" (View Location) button linking out to a maps URL.
6. **Gallery** — image grid/lightbox, no visible captions.
7. **Love story timeline** — repeatable entries, each with: title (e.g. "Awal Bertemu", "Lamaran", "Resepsi"), date, and a free-text paragraph.
8. **RSVP + Ucapan (guest wishes)** — a single combined section with:
   - Aggregate counters: total comments, count "Hadir" (attending), count "Tidak hadir" (not attending), count "Masih Ragu" (undecided)
   - A form: name, attendance status (Datang/Absen/Mungkin — Coming/Absent/Maybe), free-text message, min-length validation (2 chars), honeypot field ("Do not change these fields following...")
   - A paginated/loadable list of prior wishes (via `CUI_WP`, `jPagesNum: 10`, "Load more")
9. **Wedding hashtag** — a static display of a couple-specific hashtag (e.g. `#TiovanallywithNiko` — note: sample data shows names inconsistent with the main couple, confirming this is templated/reused test content).
10. **Wedding livestream** — date/time text + (implied) an embedded video link, shown only if provided.
11. **Wedding gift** — intro text + a modal/section listing one or more bank/e-wallet accounts, each with: account holder name, account number, provider/bank name, and a "Copy Number"/"Copy Text" button (clipboard interaction, client-side only).
12. **Closing** — closing Islamic phrase ("Wassalamualaikum Wr. Wb"), signature line ("Kami Yang Berbahagia, Kedua Mempelai & Keluarga Besar"), and a footer credit ("Designed By Website Invitation").
13. **Background music** — a single `<audio>` element, autoplay-on-gesture (tied to the cover screen's "Buka Undangan" click), a mute/unmute toggle, and pause-on-tab-hidden / resume-on-visible behavior.
14. **Guest-name personalization** — client-side JavaScript reads `?to=`, `?dear=`, or `?kepada=` from the URL query string, HTML-entity-decodes it, and injects it into every element with class `.namatamu`, falling back to "Tamu Undangan" (Generic Guest) if absent.

**Follow-up verification (closes prior "not confirmed" gaps):** a full text-content pass on all three samples confirms RSVP+Ucapan, Wedding Hashtag, and Wedding Livestream are present in **all three** templates — the earlier draft of this table under-counted betawi-motion and arjuna-tema-foto because those sections weren't visible in the first excerpt pulled from each file. All three samples also reuse the identical placeholder hashtag text (`#TiovanallywithNiko`), confirming it's vendor demo content, not real per-couple data, and should not be treated as a meaningful per-template difference. One genuine positional difference did surface: the religious quote block appears **in the hero** for raden-motion but **near the closing/footer** for betawi-motion (same verse, different placement) — so section *order*, not just section *presence*, varies by template.

**What this means for the platform, concretely:**

1. **Two tiers of features exist, and it's important not to conflate them:**
   - **Universal, plugin-level features** present in all three samples regardless of template: RSVP/Ucapan, wedding hashtag, wedding livestream, wedding gift with copy-to-clipboard, background music, guest-name personalization, QR code generation, and guest-list export. These come from the shared `weddingpress` plugin infrastructure, not from any individual template's design — so in the new platform they belong in `templates/shared/` and in the core, template-agnostic feature set, not gated behind any per-template manifest flag.
   - **Genuinely template-specific, visual/structural features**, which really do vary: pantun (betawi-motion only), hero background video (betawi-motion only), embedded video within the gallery/love-story area (betawi-motion, arjuna-tema-foto — different embed sources, YouTube vs. hosted `.mp4`), a religious quote block that's present in two of three but at *different positions* (hero for raden-motion, near closing for betawi-motion), and image-based vs. widget-based countdown rendering.
2. **Sections must be optional, composable, AND independently orderable per template**, not a fixed pipeline — but this now applies specifically to the second tier above, not the first. A template is a *specific ordered subset* of available section types, each with its own visual implementation, plus zero or more section types unique to that template.
3. **New, template-specific section types will keep appearing** as more templates are onboarded. The architecture must make adding a new section type or template a **contained, additive change** — new folder + registry entry — never a rework of existing templates or the shared schema.
4. **The core data model (couples, events, gallery, story, wishes, gift accounts) stays universal across all templates** — every sample confirms the same underlying entities, just rendered differently. Template-specific extras (pantun text, hero video URL, religious-quote position) are modeled as **optional fields scoped to `invitation_id`**, populated only when the chosen template uses them, never forcing schema changes on unrelated templates.
5. **QR generation and guest-list export are corrected to universal features** (see note below) — they move out of the template-manifest-gated feature list and into the standard feature set every invitation gets, regardless of template.

*(Correction note: an earlier draft of this PRD initially checked the QR/export libraries only against arjuna-tema-foto and marked them "not observed" for the other two. A full re-check confirms both libraries load identically across all three samples — the earlier per-template distinction was a gap in verification, not a real product difference.)*

### Data relationships (inferred)

Because content is baked into HTML rather than fetched, the underlying WordPress data model cannot be directly confirmed. Based on the product being a reusable template (the "Web Invite" business sells this to many couples), the most probable existing shape **(inferred)** is:

- One WordPress **post** (`post_id: 62777` in this sample) per invitation/customer, of a custom post type, holding all invitation fields as post-meta (ACF-style).
- Guest wishes attached as native WordPress **comments** on that post (`commentCount: 4` in the JSON-LD schema block confirms this).
- No evidence of a separate guests/RSVP table — attendance status is likely stored as **comment-meta** on each comment (this is a common pattern for this class of plugin), not a first-class relational entity.

This PRD does **not** attempt to replicate this inferred internal shape. Instead, Database Design below proposes a clean relational schema fit for the new stack, informed only by the *observable features*, not the old implementation.

No REST dependency to port — content is server-rendered, not fetched. Safe to drop entirely. |

| `wp-content/uploads/...` (images, fonts) | All `@font-face` `src` URLs; all image `src`/`srcset`; audio file `src` | Must be extracted/re-sourced and re-hosted from the new app's own asset storage (see Migration Strategy — Assets). |
| `wp-content/plugins/weddingpress/` | Audio widget, RSVP/Ucapan widget, guest-name-personalization script, gift/bank-account widget | Reimplemented natively in React (see Functional Requirements). |
| `wp-content/plugins/elementor` + `elementor-pro` | Overall page rendering, lightbox, section/container layout, breakpoints config | Reimplemented as ordinary React components + Tailwind responsive utilities. |
| `wp-content/themes/hello-elementor` | Base theme, header/footer scaffold | Not needed — new app has its own layout shell. |
| LiteSpeed Cache | Page/asset caching, deferred JS loading (`type="litespeed/javascript"`) | Replaced by standard Vite build output + HTTP caching headers set by the Hono server / reverse proxy (Cloudflare Tunnel-friendly). |
| `wp-content-copy-protector` | Anti-copy-paste / right-click protection (implied by plugin name; behavior not confirmed in static export) | Out of scope for v1. Optional client-side deterrents can be added later (Future Enhancements) — note these are always bypassable and provide no real protection. |
| Slim SEO (JSON-LD `@graph` schema) | Structured data block at bottom of `<head>`/`<body>` | Reimplemented as a small SEO-metadata module generating per-invitation JSON-LD + Open Graph/Twitter tags server-side. |
| WordPress oEmbed | `<link rel="alternate" type="application/json">` discovery tags | Not needed; standalone app is not embeddable via WordPress oEmbed and does not need to be. |

**Bottom line:** there is no wp-json data-fetching dependency to remove from the *frontend*, because the current frontend doesn't fetch invitation data dynamically at all — it's baked into server-rendered markup per WordPress post. The real migration work is (a) building an API + admin panel that doesn't currently exist in equivalent form for you to control, and (b) reproducing the interactive widgets currently supplied by the closed-source `weddingpress` plugin.

## Target Architecture

```
┌─────────────────────────────────────────────────────────┐
│                        Client (Browser)                  │
│  React + TypeScript + Vite + TailwindCSS + shadcn/ui      │
│  - Public invitation viewer (per-slug)                    │
│  - Admin dashboard (auth-gated)                            │
└───────────────────────────┬───────────────────────────────┘
                            │ REST (JSON) over HTTPS
┌───────────────────────────▼───────────────────────────────┐
│                       Backend (Hono)                       │
│  - /api/invitations/:slug   (public read)                  │
│  - /api/invitations/:slug/wishes  (public write + read)     │
│  - /api/admin/*             (auth-gated CRUD)               │
│  - /api/uploads             (asset ingestion)                │
│  - Session/auth middleware                                  │
└───────────────────────────┬───────────────────────────────┘
                            │ Drizzle ORM
┌───────────────────────────▼───────────────────────────────┐
│                     SQLite (file-based)                    │
│  invitations, couples, events, gallery_images, story_items, │
│  wishes, gift_accounts, admin_users, invitation_assets       │
└─────────────────────────────────────────────────────────────┘

              All packaged as Docker Compose services,
        fronted by Cloudflare Tunnel, no WordPress/PHP/MySQL.
```

Key architectural decisions:

- **Multi-tenant by design.** Every table is scoped by `invitation_id`, so the platform can serve many couples' invitations (matching the observed template-product nature of the source), each reachable at its own slug (`/raden-motion`, etc.) and shareable with a personalized guest-name query parameter, preserving the current `?to=`/`?dear=`/`?kepada=` UX.
- **Static-first, API-backed.** The public invitation view is a single Vite-built SPA route that fetches one JSON payload (`GET /api/invitations/:slug`) on load, then renders all sections client-side — replacing "bake everything into server HTML" with "fetch once, render client-side," which is simpler to cache and CDN-friendly.
- **Assets served by the app, not linked to a third party.** Uploaded images/fonts/audio live under a Docker volume, served by the Hono app (or an Nginx sidecar) — no more hot-linking to `webinvite.id`.

## Non-Functional Requirements

- **Performance:** Public invitation page should reach Largest Contentful Paint under 2.5s on a throttled 4G connection; total JS bundle for the public viewer under 250KB gzipped (excluding fonts/images/audio).
- **Availability:** Self-hosted on your existing Proxmox/Docker Compose setup; no hard dependency on third-party SaaS beyond Cloudflare Tunnel (already in your stack).
- **Scalability:** SQLite is appropriate for expected load (personal/small-business scale, one file per deployment); document a clear upgrade path to a networked Postgres if guest-wish volume or concurrent invitation count grows substantially (see Future Enhancements).
- **Maintainability:** No proprietary/closed-source plugin dependency; the entire stack is code you own and can read/modify.
- **Accessibility:** Form fields (RSVP, wish submission) must have proper labels and be operable via keyboard; countdown and audio-toggle controls must have accessible names.

---

## Security Requirements

- **RSVP/Wish endpoints are public-write.** Rate-limit by IP + invitation slug; add a honeypot field (preserving the current "Do not change these fields following..." pattern) and basic spam heuristics (min/max message length, duplicate-submission throttling).
- **Admin authentication:** session-based auth (signed, httpOnly cookies) for the admin panel; passwords hashed (e.g. argon2/bcrypt). No public registration — admin accounts provisioned directly.
- **Input sanitization:** All guest-submitted text (name, wish message) must be sanitized/escaped before rendering to prevent stored XSS — a real risk area given the old system rendered comments as raw-ish HTML via a WordPress comment plugin.
- **File uploads:** Validate MIME type and size for gallery images, couple photos, and background audio; store outside any web-executable path.
- **Guest-name query parameter:** Must be HTML-escaped on render (the old implementation manually stripped some HTML entities; the new implementation must treat this as untrusted input and escape it properly, since it is fully attacker-controlled via a shared URL).

---

## Performance Requirements

- Lazy-load gallery images below the fold.
- Serve background audio and images with proper cache headers (`Cache-Control: public, max-age=...` + content-hashed filenames) since these are static once uploaded.
- Avoid loading the admin dashboard's JS bundle on the public invitation route (separate route-level code splitting).

---

## SEO Requirements

- Per-invitation `<title>`, meta description, canonical URL, Open Graph and Twitter Card tags (image, title, description) — matching the OG/Twitter image tags observed in the source.
- JSON-LD structured data for the event (schema.org `Event` type is more appropriate than the old site's generic `WebPage`/`Article` schema, and should be adopted going forward).
- Server-side rendering or a pre-render/SSG step for the invitation route specifically, since guest-facing links are shared via WhatsApp/social and need working link-preview scraping (a pure client-rendered SPA will not produce correct OG tags for link unfurls).

## Mobile Responsiveness

The overwhelming majority of guests will open invitations on mobile (shared via WhatsApp). Design mobile-first with Tailwind; the current source's breakpoint config (mobile ≤767px, tablet ≤1024px) is a reasonable reference but should be re-evaluated against shadcn/ui + Tailwind defaults rather than copied verbatim.

| Role | Access |

| Guest (public) | View invitation, submit RSVP + wish, view others' wishes, copy gift account numbers, view gallery/story, toggle music. |
| Couple/Owner | All guest access, plus: full CRUD on their own invitation's content via the admin panel; moderate wishes; view RSVP stats and basic visit analytics. |
| Super Admin (you) | Manage all invitations across tenants; create/deactivate couple accounts; global stats. |

## User Flow (Guest)

1. Guest opens a shared link, possibly with `?to=GuestName`.
2. Cover screen shows "The Wedding Of [Names]", "Kepada Yth: [GuestName or default]", and an "Open Invitation" button.
3. On click: cover dismisses, background music begins (browser-compliant, gesture-triggered), and the guest scrolls through hero → greeting → couple profiles → event details (with map link-outs) → gallery → story timeline → RSVP/wishes → hashtag → (optional) livestream → gift → closing.
4. Guest submits RSVP + optional wish; sees updated aggregate counts and their entry appear in the wish list.
5. Guest can copy a gift account number or the invitation link itself (with their name param preserved) to share onward.

## Admin Flow (Couple/Owner)

1. Log in to the admin dashboard.
2. Fill in couple data, events, gallery, story, gift accounts, hashtag, and upload background music — each as a discrete CRUD form, mirroring the public sections 1:1.
3. Preview the public invitation at any point.
4. Publish/share the slug-based link, optionally generating a QR code.
5. Monitor RSVP counts and moderate incoming wishes (hide spam/inappropriate entries) from a single dashboard view.

## Database Design

### Entities

- **invitations** — one row per couple/wedding. `id`, `slug` (unique), `owner_user_id`, `title`, `opening_greeting_text`, `closing_text`, `quote_text`, `quote_source`, `cover_guest_label_default` (e.g. "Tamu Undangan"), `hashtag`, `theme` (optional visual variant key), `is_published`, `created_at`, `updated_at`.
- **admin_users** — `id`, `email` (unique), `password_hash`, `role` (`owner` | `super_admin`), `created_at`.
- **couples** — one row per side (bride/groom) per invitation. `id`, `invitation_id` (FK), `role` (`bride`|`groom`), `full_name`, `display_name`, `father_name`, `mother_name`, `birth_order_label` (e.g. "Putri Kedua"), `instagram_handle`, `photo_asset_id` (FK → invitation_assets).
- **events** — `id`, `invitation_id` (FK), `label` (e.g. "Akad Nikah"), `date`, `start_time`, `end_time_label`, `venue_name`, `venue_address`, `maps_url`, `sort_order`.
- **gallery_images** — `id`, `invitation_id` (FK), `asset_id` (FK), `caption` (nullable), `sort_order`.
- **story_items** — `id`, `invitation_id` (FK), `title`, `date`, `description`, `sort_order`.
- **wishes** — `id`, `invitation_id` (FK), `guest_name`, `attendance_status` (`attending`|`not_attending`|`maybe`), `message`, `is_hidden` (bool, for moderation), `created_at`.
- **gift_accounts** — `id`, `invitation_id` (FK), `holder_name`, `account_number`, `provider_name` (bank/e-wallet name), `sort_order`.
- **invitation_assets** — `id`, `invitation_id` (FK), `kind` (`image`|`audio`|`font`), `storage_path`, `mime_type`, `original_filename`, `created_at`.
- **livestream_info** *(optional per invitation)* — `id`, `invitation_id` (FK), `label`, `date`, `time_label`, `stream_url` (nullable).
- **templates** — one row per available template/theme, sourced from each template's manifest (see Folder Structure below), not user-editable via the app: `id` (matches folder/registry key, e.g. `raden-motion`), `display_name`, `preview_image_path`, `supports_pantun` (bool), `supports_hero_video` (bool), `quote_block_position` (enum: `hero` | `closing` | `none`), `gallery_video_type` (enum: `none` | `youtube` | `hosted`), `is_active` (bool, to retire old templates without deleting history). *(Note: QR code generation and guest-list export are universal platform features available to every invitation regardless of template — see Functional Requirements #18–19 — so they are deliberately NOT modeled as per-template flags here, correcting an earlier draft that mistakenly gated them behind arjuna-tema-foto only.)*

Only populated for fields the invitation's chosen template actually declares.

## Frontend Architecture

- **Routing:** `/` (marketing/landing, optional), `/i/:slug` (public invitation viewer — resolves the invitation's `template_key` and renders the matching template), `/admin/*` (dashboard, code-split separately).
- **Data fetching:** a single `useInvitation(slug)` hook wrapping one `GET /api/invitations/:slug` call, returning the universal payload (couples, events, gallery, story, wishes, gift accounts, plus `template_key` and any populated `invitation_template_fields`); React Query (or a lightweight fetch+cache wrapper) for the admin CRUD screens.
- **Template resolution:** the public route does **not** know about individual templates directly. It looks up `template_key` in a central `templates/registry.ts`, gets back the matching template's root component, and renders it with the fetched payload as props — identical contract for every template, present or future.
- **Component structure inside each template:** one presentational component per section used by that template (`CoverGate`, `HeroCountdown`, `CoupleProfiles`, `EventDetails`, `Gallery`, `StoryTimeline`, `RsvpAndWishes`, `Hashtag`, `Livestream`, `WeddingGift`, `ClosingFooter`, plus template-specific ones like `PantunBlock` or `HeroVideoIntro`), each fed purely by props — no component fetches its own data, keeping every template simple and cache-friendly.
- **Cross-template shared behavior** (background music playback, guest-name query-param injection, copy-to-clipboard, QR generation) lives once in `templates/shared/`, imported by whichever templates need it — never duplicated per template.
- **Styling:** Tailwind + shadcn/ui primitives (Button, Dialog for the gift modal, Form components for RSVP) for the admin panel; each template's public-facing visual layer is free to have its own look (fonts, colors, animations) scoped to its own folder, since templates are explicitly meant to look different from one another.

### Why this structure specifically answers "banyak template"

1. **One template = one self-contained folder** under `templates/`. Nothing about onboarding raden-motion, betawi-motion, or arjuna-tema-foto (or template #4 onward) requires touching another template's files, the database schema, or the API — confirmed by the fact that all three real samples share the same core entities (couples, events, gallery, story, wishes, gift accounts) despite having different extra sections.
2. **`registry.ts` is the single lookup point.** The public viewer route does one thing: read `template_key` from the fetched invitation, look it up in the registry, render the result. Adding a template means adding one line to this file — never branching logic elsewhere in the app.
3. **`manifest.json` per template is what makes the admin panel dynamic.** It declares only the flags that genuinely vary between templates — `supportsPantun`, `supportsHeroVideo`, `quoteBlockPosition`, `galleryVideoType`. Universal features (RSVP, hashtag, livestream, gift, QR code, guest-list export) are **not** manifest flags — they belong to every invitation regardless of template, and are never gated. The admin "template-fields" form (`features/admin/template-fields/`) reads the manifest to decide which *extra, template-specific* fields to show — e.g. only show a "Pantun text" input when editing an invitation using betawi-motion — while the universal features always appear.
4. **`shared/` prevents duplicated logic** for behavior that's identical across templates (music player, guest-name injection, clipboard copy, QR generation) even though the three samples implement it via three different closed-source widgets today (`weddingpress-audio`, `weddingpress-wellcome`, `weddingpress-copy-text`, `qr-code-styling`). Write each behavior once, let every template's `index.tsx` import what it needs.
5. **The database never needs a template-specific migration.** New optional content (pantun, hero video URL, etc.) goes into the generic `invitation_template_fields` key-value table, keyed by whatever field names that template's manifest declares — so onboarding template #4 with a brand-new kind of field (say, a "family crest image" for a Javanese-adat template) needs zero schema changes, only a new manifest entry and a new section component.
6. **Assets stay template-scoped vs. invitation-scoped, deliberately.** Fonts and decorative graphics that belong to the *design* of a template live in `templates/{slug}/assets/` (checked into the repo, shipped with the app). Actual user content — a couple's real photos, their chosen background song — lives in `storage/uploads/{invitation_id}/` (runtime data, never checked into git, backed by a Docker volume). This mirrors exactly the distinction the WordPress analysis surfaced: template-bundled fonts/graphics vs. per-post `wp-content/uploads` media.

## Backend Architecture

- Hono app with route modules split by resource (`invitations.ts`, `wishes.ts`, `admin/*.ts`).
- Drizzle ORM schema colocated in `src/db/schema.ts`; migrations via `drizzle-kit`.
- Session auth via a small middleware checking a signed cookie against a `sessions` table (or a JWT if you prefer statelessness — either is reasonable at this scale; recommend simple DB-backed sessions given SQLite is already in the stack).
- File uploads handled via Hono's built-in body parsing, streamed to a local volume path, referenced by `invitation_assets`.

## Component Architecture

Standard container/presentational split: route-level components own data fetching (public viewer, admin pages); section components are pure/presentational and unit-testable in isolation, matching your existing TypeScript/React experience.

## State Management Strategy

No global state library needed for the public viewer — one fetched payload passed down via props/context is sufficient given the page's read-mostly nature. For the admin panel, React Query (or equivalent) for server-state caching/invalidation after CRUD mutations; local component state (useState) for form editing.

## Migration Strategy

Since there is no existing source to incrementally migrate for any of the three templates, "migration" here means a **staged rebuild + content re-entry**, not a code port — and, because there are already three templates (with more expected), the rebuild is designed from day one to onboard N templates through one repeatable process rather than being built around a single invitation.

### What can be reused
- The observed **information architecture** (section order, field list, and — critically — the per-template *variability* documented in Template Catalog & Variability) directly informs the schema and folder structure above.
- The **copy/content** of these three specific invitations (names, dates, story text, pantun, etc.) can be manually re-entered into the new system as seed/demo data, one per template, doubling as each template's working example during development.
- Visual/UX reference for spacing, animation style, and interaction patterns (cover gate, audio toggle, copy-to-clipboard, hero video, QR flow) — reproduced newly per template, not copied as code.

### What must be rewritten from scratch
- 100% of the implementation for all three templates: no Elementor markup, no `weddingpress` plugin code, and no WordPress data model can be reused, since none of it is present in a portable form (see scoping note).
- All fonts, images, and video/audio assets must be re-sourced **per template**. Many of the custom fonts observed across the three samples (`Amiri-Bold`, `Allura`, `Lobster`, Google-Fonts-hosted families like Open Sans/Italianno/Bilbo, and several "personal use only" trial fonts such as `Adlery_TRIAL` and `FortalesiaPlain_PERSONAL_USE_ONLY`) carry licensing terms that likely **do not permit reuse in a new commercial product** — see Risk Assessment. This audit must be repeated for every template's own font/asset set, not just raden-motion's.

### Staged plan

1. **Stage 0 — Foundation.** Scaffold monorepo (Vite React app + Hono API), Drizzle schema (including `templates` and `invitation_template_fields`), Docker Compose, base auth, and the `templates/registry.ts` mechanism itself — built and tested against **at least two** of the three templates from the start, so the "multi-template" abstraction is proven early rather than retrofitted after one template ships.
2. **Stage 1 — Static sections, first template.** Build read-only public viewer for raden-motion's sections (cover, hero/countdown, religious quote, couple profiles, events, gallery, story) — seeded with its re-entered content, no admin panel yet (seed via SQL/JSON fixture).
3. **Stage 1b — Second and third templates, static sections.** Add `betawi-motion/` and `arjuna-tema-foto/` folders, reusing `shared/` where behavior overlaps and adding template-specific sections (`PantunBlock`, `HeroVideoIntro`, `CountdownGraphic` for betawi-motion; renamed story entries, embedded video, `amplop` toggle for arjuna-tema-foto). This stage is the real proof that the folder structure holds up — treat any friction here as a signal to revisit the registry/manifest design before a 4th template arrives.
4. **Stage 2 — Interactive sections, all templates.** RSVP + wishes (read + write), gift accounts + copy-to-clipboard, hashtag, background music, guest-name query param, QR generation (for templates whose manifest enables it) — implemented once in `shared/`, wired into each template that needs it.
5. **Stage 3 — Admin panel.** Auth + full CRUD across all resources; template picker with preview (`GET /api/templates`); dynamic template-fields form driven by manifest; wish moderation; asset upload; guest-list export.
6. **Stage 4 — SEO/sharing.** OG/Twitter tags, JSON-LD, QR generation, share/copy-link — per template, since preview images and titles differ per invitation regardless of template.
7. **Stage 5 — Polish & hardening.** Rate limiting, input sanitization audit, mobile QA, performance pass — run once across all three templates, not just one.

### Onboarding a new template (post-launch checklist)

Once the platform is live, adding template #4 and beyond should follow this fixed checklist — this is the operational payoff of the folder structure above:

1. Create `apps/web/src/templates/{new-slug}/` with `index.tsx`, `manifest.json`, `sections/`, `styles.css`, `assets/`.
2. Fill in `manifest.json`'s feature flags (`supportsPantun`, `supportsHeroVideo`, `quoteBlockPosition`, `galleryVideoType`, etc. — genuinely template-specific variations only) truthfully for what this template actually renders. Universal features (RSVP, hashtag, livestream, gift, QR, export) need no flag — every template gets them by default via `shared/`.
3. Build each section component, reusing anything already in `templates/shared/` (music player, guest-name injector, copy button, QR generator) rather than reimplementing it.
4. Add one line to `templates/registry.ts` mapping the new `template_key` to this template's root component.
5. Add a seed row to `templates` table (or let `db/seed/templates.ts` pick it up automatically from the new `manifest.json` at next deploy).
6. No changes required to: the database schema (beyond an optional new `invitation_template_fields` key, if the template introduces a genuinely new field type), the API routes, or any other template's code.

### Breaking changes
- Guest-facing URLs will change (new domain/slug scheme) — any previously shared links (`webinvite.id/raden-motion/?to=...`, `webinvite.id/betawi-motion/?to=...`, `webinvite.id/arjuna-tema-foto/?to=...`) will need a redirect plan if continuity matters, or can simply be treated as a fresh product per invitation.
- Guest wishes previously stored as WordPress comments are **not automatically portable** for any of the three (no export was provided in-scope); if historical wishes need to be preserved for a specific past invitation, that requires a separate WordPress-side export step not covered by this PRD.

## Risk Assessment

| Risk | Impact | Mitigation |
|---|---|---|
| Font licensing. Several fonts observed across all three templates (trial/personal-use fonts, and any bundled with the `weddingpress` product) may not be licensed for reuse in a new, independently distributed product. | Legal/IP exposure if shipped as-is. | Before launch, audit every font actually needed **per template** and replace unlicensed ones with equivalents from Google Fonts or a properly licensed foundry. Do not carry over `*_TRIAL`/`*_PERSONAL_USE_ONLY` files for any template. |
| Image/video assets (backgrounds, mockup photos, the betawi-motion hero video, embedded videos in betawi-motion and arjuna-tema-foto) belong to the original site/product and possibly to the real couples photographed. | Copyright/privacy exposure. | Use only assets you own the rights to, or each real couple's own uploaded photos/video going forward — do not port stock imagery or video from any of the three samples. |
| Inferred data model may not match every edge case the old plugin supported across all three templates (e.g. multiple songs, additional social links, the exact purpose of the `kirimkit`/xlsx export seen only in arjuna-tema-foto). | Feature gaps discovered late. | Treat Stage 1–3 as intentionally scoped to the *confirmed observed* feature set per template; explicitly punt undiscovered edge cases to Future Enhancements rather than guessing. Re-run this same static-analysis process on each new template zip before onboarding it, rather than assuming it matches an existing one. |
| A 4th, 5th, or Nth template introduces a section type genuinely unlike anything in the first three (discovered only when that zip is analyzed). | Registry/manifest design proves too rigid, forcing a rework. | Stage 1b is explicitly designed to stress-test the abstraction with 2 templates before any others are onboarded; if betawi-motion or arjuna-tema-foto reveal the pattern doesn't hold, resolve it there — with only 3 templates' worth of rework — rather than after 10 templates exist. |
| SQLite concurrency limits if this becomes a multi-tenant SaaS with meaningful concurrent write load (many simultaneous RSVP submissions across many weddings). | Write contention under load. | SQLite's WAL mode handles moderate concurrent load fine for this use case; document a clear migration path to Postgres if/when scale demands it — do not over-engineer for this on day one. |
| RSVP/wish spam once the closed-source plugin's (unknown) anti-spam logic is gone. | Content quality/moderation burden. | Implement honeypot + rate limiting + basic profanity/length checks from Stage 2 onward (see Security Requirements). |

## Testing Strategy

- **Unit tests:** Drizzle schema constraints, wish-submission validation logic, guest-name query-param parsing/escaping.
- **Integration tests:** Hono route handlers against an in-memory/temp SQLite DB (create invitation → add event → fetch public payload → assert shape).
- **E2E (optional, Playwright):** cover-gate → RSVP submission → wish appears in list; admin login → edit couple name → public page reflects change.
- **Manual QA:** cross-browser audio autoplay behavior (Safari iOS has stricter gesture requirements than Chrome — must be explicitly tested), mobile responsiveness at common breakpoints.

## Deployment Strategy

- Docker Compose services: `app` (Hono, serving built Vite assets too, or split `web`/`api` containers if you prefer), SQLite as a mounted volume file (not a separate container — it's embedded).
- Fronted by your existing Cloudflare Tunnel setup, consistent with your current self-hosted infra pattern.
- Environment-based config for session secret, upload storage path, and (optionally) an S3-compatible bucket if you later want asset storage off the local disk.
