# Riska & Rafli — yt-wedding integration design

**Status:** Design approved in conversation; written specification awaiting review. **Date:** 2026-11-02. **Target:** `https://you-are-invited.my.id/i/riska-rafli`.

## Intent and non-negotiables

Add a separately managed Riska & Rafli invitation to the existing multi-client platform without changing Anggi & Ivan's invitation. Preserve the original `yt-wedding` invitation's visible HTML structure, classes, CSS, fonts, icon geometry, typography, layout, responsive behavior, and animations **1:1** whenever a section is shown. Only adapt content bindings, local asset paths, platform-specific scripts, and broken interactions. `CLAUDE.md` visual-fidelity rule takes precedence over PRD rebuild advice. Do not imply that an unverified payment, check-in, statistic, or video playback succeeded.

Client content and permission to publish bundled assets are not yet available. Create an unpublished, super-admin-managed draft. The production URL must not expose Juliet & Romeo or placeholder dates, photos, bank details, and social metrics. The draft may show clearly identified missing-data markers in an authenticated preview, but cannot become public until an admin explicitly publishes it after verifying content, visual parity, asset rights, external links, and YouTube-related trademark use. Do not silently substitute fonts, images, or artwork when rights are unresolved: keep the draft unpublished.

## Architecture and delivery boundary

1. **Template presentation:** Add `yt-wedding` as a distinct template key and standalone HTML/CSS/JS asset set, based on the captured DOM rather than rewriting sections as React. Keep original visual rules intact. A thin template-specific binding layer maps a single invitation-scoped API payload into the existing element positions via DOM-safe text and validated URL/asset assignments. Keep generic shared behaviors (asset delivery, wish API, metadata, admin authentication) in the existing platform. Do not run bundled scripts blindly: preserve original motion and interaction behavior while removing platform-specific network/preview/tracking logic.
2. **Routes:** Published `/i/riska-rafli` uses the normal backend page route and matching payload. A separate authenticated, no-store backend preview route serves drafts only after checking caller's session and invitation ownership/role; `?preview=` alone is never authorization. Block unauthenticated direct access to client-specific static HTML and any parallel dev/production path that exposes unpublished content. The draft's public page and API return not-found. Keep Anggi route and files unchanged.
3. **Ownership:** Scope every admin list/read/write, media upload/deletion, nested resource, and publication action to the invitation owner, except super admin. Initially the draft belongs to super admin. No invented client account or credentials. Add explicit admin publish/unpublish control with confirmation and validation gates; no auto-publication when fields are populated.
4. **Isolation:** Store Riska-specific records and uploads under their own invitation ID, never mutate Anggi records or production HTML. Template design assets are static and distinct from client-uploaded photos/audio/video. Only seed the template catalog and unpublished Riska draft once; never overwrite populated client data on restart.
5. **Metadata:** Backend renders title, description, canonical, OG and Twitter tags for the relevant published client in initial HTML. Preview responses must not be indexed or shared as production previews; published WhatsApp preview resolves Riska-specific approved image.

## Dependency and asset migration

- Remove HTTrack comments, Chara attribution/viral CTA and `/mulai` redirect, `charaEventMode`/preview interception where platform-specific, Chara RSVP endpoint, Chara analytics/beacon and Cloudflare challenge injection. Confirm purpose before removing anything that affects an actual animation, modal, or UI state. Retain legally required attribution if rights review establishes one; absence of proof is a publication blocker, not permission to erase it.
- Bundle/build equivalent Tailwind classes without changing computed values; mirror actual font binaries, icon font binaries, images, animation assets and audio only with proven distribution rights. Verify all relative CSS `url(...)`, script imports, image URLs, and built network requests. Roboto/Font Awesome and YouTube identity need rights/trademark review. No runtime `chara.id` requests; target platform may still use services genuinely required by its own API (e.g. anti-spam), but none may silently supply template assets or fabricated QR check-in.
- Strengthen upload boundary: accept only needed image/audio/video media, enforce per-kind size, extension/MIME/signature, safe paths, invitation ownership and cleanup on failure. Keep replacements within original `object-fit` and geometry. No uploads to Anggi assets for this invitation.

## Validation and release gates

- Run reproducible assertions for page draft/public access, owner versus super-admin permissions, invitation scoping, admin save/read-back, asset validation, RSVP status/channel/pax, moderation, `?to=` escaping, client-specific metadata, and Anggi regression. Include checks that seeded draft does not mutate existing clients.
- Browser-check source versus converted template at desktop/tablet/phone widths with the **same permitted visual assets and content**; compare cover, visible sections, modals, transitions, fixed navigation, and mobile scrolling/overflow. Verify real upload replacements stay inside original frames. Distinguish pre-existing source defects from conversion regressions.
- Inspect console/network/build for missing fonts, images, CSS, JS, 404s, `chara.id` references, Cloudflare beacon, `api.qrserver.com`, false-success UI, and unapproved third-party runtime loads. Check OG/WhatsApp tags from initial HTML, not only DOM after JavaScript. Re-test Anggi page and dashboard unchanged.
- **Not production-ready yet:** no client content, no approved asset licenses, no verified YouTube trademark use, incomplete source snapshot for gift tiers/payment success, and no check-in/payment backend. Keep unpublished until applicable gates pass; report each gap explicitly rather than claiming production readiness.

## Implementation boundaries

Prefer existing API, schema, and admin patterns; add only columns/configurations necessary for persisted RSVP channel/pax and template-specific content. Preserve existing invitation behavior and migration safety. Written implementation plan must sequence: access isolation and draft preview, template/asset audit and permission gates, schema/API changes, dashboard fields, faithful HTML binding, and regression/browser validation. No product implementation begins until this written design is reviewed and its plan separately approved.
